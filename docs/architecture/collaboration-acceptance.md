# Agent 协作架构：实施与验收基线

更新：2026-10-05。状态：**W01—W08 已实现并完成本版验收，外部账户联调边界见验收记录**。产品与模型约束以[目标架构](agent-collaboration.md)为准；当前代码能力见[代码现状](code-framework.md)。

本计划覆盖整个仓库，目标是可实际使用的人机协作闭环。工作包用于组织开发和验证，不是旧、新两套架构渐进兼容的发布计划。旧数据无需兼容；当前文档只描述现行主链。

## 1. 交付边界

用户只需持续与接待 Agent 交流，就能提出需求、补充信息、调整工作、查看结果、暂停或确认成果。Agent 负责 Task 和执行实例的组织。后台实例拥有真实 Session 和可恢复上下文。参与者可以按授权直接协作，最终决定有明确责任人和依据。

必做：统一实例、消息/唤醒、Task 信息与决定、角色模板、工具授权、接待入口、流程工具、资源引用、跨角色端到端验证。

后续：完整企业组织管理产品、复杂交接审批、任意自创角色、高级预算优化、多租户部署产品化、全套性能/SLO 平台。基本权限、持久性、取消和幂等不推迟。

### W02：统一 Session 执行与持久上下文

- [x] 所有 Agent 激活必须解析真实 Session 和实例身份。
- [x] 合并当前 Session 推理与 Task Agent 执行分支，移除伪 Session、无 transcript 路径。
- [x] 记录输入、模型可记录输出、工具请求/结果、检查点、失败及可恢复状态。
- [x] 委派创建或联系独立 Agent 实例，保持各自身份和持续上下文。
- [x] 分开实例生命周期、Activation 状态、工具等待和计算资源占用。
- [x] 加入长期上下文的分页、工作摘要、来源引用与按需读取；保留未完成工作和决定。
- [x] 检查 transcript 保留策略、Redis TTL、Session 空闲结束和 Temporal 历史轮换，保证活跃工作不会被清理破坏。
- [x] 取消或失败后的副作用回执可核对，恢复不能伪装成从未发生过的调用。

重点位置：`AgentService`、`AgentDispatcher`、`AgentStore`、`ActivationWorkflowImpl`；Runtime 的 `main.py`、`streaming.py`、`transcript_store.py`、`context_budget.py`、`prompting.py` 和隐私链路。

完成证据：无用户页面在线时，后台实例仍有可查询上下文；重启后继续同一实例；两个同模板实例互不串历史。调用次数、内存驻留和实例存在时间不再相互等价。

### W03：工具授权与代理决定

- [x] 工具执行上下文由服务端绑定主体、Session、Activation、授权范围及来源，模型参数不能伪造身份。
- [x] 所有内置协作工具、资源工具、流程子工具使用统一授权语义。
- [x] 模板挂载工具与实际授权分开；执行权限和转授权权限分开。
- [x] 背景装配、历史查阅和资源读取使用相同的权限过滤。
- [x] 用户明确指令产生可追溯决定，由 Agent 代理调用；保留原消息、目标与相关版本。
- [x] 对无关旧消息、伪造用户身份、已撤销授权、越界对象和流程/脚本越权提供明确拒绝结果。
- [x] 人直接操作 UI/API 与 Agent 工具调用复用业务服务，不复制三套规则。

现有 `PlatformAuthorization` 的平台角色门禁不能替代对象授权。现有 `TaskAccess` 的协作能力和连接器凭证处理可以重用，但当前 `VIEW/CONTRIBUTE/.../MANAGE` 命名不作为新模型不可修改的前提。

完成证据：Agent 能合法提交自己的成果，不能凭自身权限替用户最终确认；收到具有权限的用户明确指令后能代理执行并正确记录责任；撤销后旧配置快照不继续授予权限。

### W04：消息、持久投递与唤醒

- [x] 人→Agent、Agent→Agent、Agent→人采用同一参与者消息语义，区分消息、投递与业务处理结果。
- [x] 建立持续接待绑定；同一接待关系恢复原 Session，普通用户无须选择实例。
- [x] 以发件箱/收件记录承接输入，再触发执行；明确失败与重复投递的处理。
- [x] 支持订阅相关 Task/资源变化、定时唤醒、查询和取消安排。
- [x] 工具结果、人工回应和外部回调定位具体 Session、ToolRun 和等待点。
- [x] 权限过滤后投递与展示；接待入口不自动获得所有专业实例的私有记录。
- [x] 取消、停用、关闭工作时处理关联等待与调度；迟到事件不复活旧工作。

重点位置：API agent/channel 聚合、Worker 工作流与 activity、共享 Redis 和 PostgreSQL 持久层、Channel Gateway 入站/出站、Extension 协议与 SDK、Web SSE 消费。

完成证据：不同发送方的消息能唤醒正确实例；重启后未派发输入继续投递；重复回调只产生一次业务决定；定时触发不需要浏览器常驻。

### W05：Task、共享内容、成果和确认

- [x] Task 保持独立工作信息模型，允许长期事项、阶段交付、父子/依赖/相关关系。
- [x] 共享黑板保留在 Task 内；内容支持来源、版本、范围、不同意见和可用成果引用。
- [x] 发布、读取和查阅历史分别检查授权，关联 Task 不自动复制上下文。
- [x] Task 内容变动后，实例按版本感知变化；取消当前“首次选定前 N 条快照即全部长期上下文”的隐含限制。
- [x] 实例提交成果，发起者确认；代建根 Task 与自主创建子 Task 的发起归属不同。
- [x] 移除所有工作统一适用的评审数量和子任务完成阻断，按明确工作约定处理。
- [x] 自然语言的调整、暂停、否决、返工和确认调用真实业务命令。
- [x] 失败和工具完成不自动完成 Task；确认责任转交只实现必要记录与授权。

重点位置：`CollaborationService`、`TaskCommandService`、`AgentToolService`、`TaskStore`、Task 共享契约、Runtime 内置工具、成果展示组件。

完成证据：多个实例贡献同一 Task，冲突后可重新读取和协调；有权的发起者对明确成果作最终确认，决定可追溯。

## 3. 集成与回归顺序

1. W01 确定共享模型，同时设计 W02/W03/W04 所需身份与事件关联。
2. 打通一条最小真实链：用户消息 → 接待 Session → 创建 Task → 创建执行 Session → 工具成果 → 回接待实例 → 用户确认。
3. 扩展直接协作、人工等待、调度和长期上下文；完成 W02—W05。
4. 接入 W06 流程与资源能力，完成 W07 日常界面和管理区改造。
5. 执行 W08 的全仓清理与验收，确保旧主链没有残留的业务消费者。

每一阶段检查完整链路是否仍符合 D01—D21。中间编译调整可以按模块进行；不以“先保留老 Session，再做一层新 Agent 包装”作为最终方案。

## 4. 工具与事件能力

以下按职责组织已实现能力；具体工具 schema 在 Runtime `collaboration_tools.py`，HTTP 契约在 `packages/contracts/openapi/`。

| 能力 | 典型输入 | 持久输出或事件 |
| --- | --- | --- |
| 发现角色与参与者 | 需求、范围、已有工作 | 获授权的模板/参与者目录 |
| 创建或联系 Agent | 模板版本、工作背景、已有实例引用 | 实例身份、Session、协作消息 |
| 维护 Task | 目标、参与关系、共享内容、来源、期望版本 | Task 变更与贡献记录 |
| 提交与确认交付 | Task、成果版本、决定及原始消息关联 | 提交/返工/确认决定 |
| 发送与回复消息 | 接收者、Task、回复关联、内容引用 | 消息与投递状态 |
| 读取资源与历史 | 对象引用、范围、版本、查询 | 获授权内容和来源 |
| 订阅或安排唤醒 | 实例、条件或时间、有效范围 | 可查询和取消的安排 |
| 执行流程/工具 | 能力版本、对象、参数 | ToolRun、等待点、结果事件 |
| 控制工作 | 暂停/取消/接手意图、作用对象 | 控制决定和后续执行安排 |

服务端可信身份、授权和幂等关联不由模型任意构造。所有工具返回可解释的拒绝/冲突/等待结果，让 Agent 能继续组织工作。

## 5. 真实场景端到端矩阵

| 编号 | 场景与参与角色 | 必须观察到的结果 |
| --- | --- | --- |
| E01 | 普通用户、接待实例、研究实例：供应商调研 | 自然语言建 Task 和委派；后台实际调用工具；成果回原入口；用户确认结束。 |
| E02 | 同一用户连续交代采购与市场调研 | 接待实例持续存在；独立执行实例分别工作；无“开始新工作”操作；业务指代明确。 |
| E03 | 协调、研究、财务、审核 Agent | 同模板实例身份不同；Agent 可直接协作；子工作由发起 Agent 确认，总工作由用户确认。 |
| E04 | 内部负责人、外部供应商、观察者 | 各自读取获授权内容；外部参与不要求成为平台管理员；共享 Task 不泄漏私有 Session。 |
| E05 | Agent 等待人的补充 | 请求和回应关联正确工作；普通人工输入不触发全局接管；Agent 在原 Session 继续。 |
| E06 | 用户修改目标、要求返工、明确确认 | 决定归属用户，执行者是代理 Agent；原消息与成果版本可追溯；含糊指令先澄清。 |
| E07 | 越权实例、伪造代理确认、撤销授权 | 真实工具拒绝；同模板不共享授权；输入不能伪造别人的身份或借旧发布版本保留权限。 |
| E08 | 长时间工作、定时跟进、资源更新 | 安排持久化；浏览器关闭仍能触发；长期上下文整理后保留关键决定与未完成事项。 |
| E09 | API/Worker/Runtime 重启和投递重试 | 同一 Session 和 Task 接续；transcript 实际启用；未投递事件继续处理；外部写不盲目重复。 |
| E10 | 暂停、取消、人工接手与迟到结果 | 执行安排响应明确指令；旧回调不复活工作；人工承担工作但不成为 Agent Session Owner。 |
| E11 | Playbook 脚本、工具、人工/外部等待 | 作为 ToolRun 执行和恢复；结果唤醒调用 Session；流程成功不自动确认业务交付。 |
| E12 | 报告文件、知识文档、外部业务对象 | Task 引用实际可读取内容；审核实例用对应工具继续使用；权限不因引用而扩张。 |
| E13 | 两个 Agent 同时贡献和修改材料 | 版本冲突可见并可处理；贡献没有丢失；基于旧成果的确认不被套用到另一版本。 |
| E14 | 管理员配置角色和入口，用户直接使用 | 角色与入口独立配置；模型工具配置有效；实例保存实际版本依据。 |
| E15 | 一个执行实例参与有关联的多个 Task | 机制允许；上下文与消息能标明工作关联；不存在 Task↔Session 一对一硬约束。 |
| E16 | 长期职责的多次阶段交付 | 阶段确认不关闭接待实例或整个长期工作；后续事件能够继续推进。 |

### 5.1 测试真实性

沿用现有跨语言端到端测试的真实 PostgreSQL、API、Temporal worker 与 Python runtime 基础，但重写与旧语义绑定的场景。特别取消后台测试关闭 transcript/Redis 生命周期的捷径。

确定性模型供应商用于可重复地驱动多轮工具和错误分支；允许预置用户、模板、授权等测试基础数据，不得直接写入预期业务成果来绕过 Agent/工具链。重启、等待和回调必须实际经过调度与存储。

浏览器测试从日常交流入口开始，验证实时消息、进展、成果和自然语言确认。真实模型抽查至少覆盖 E01、E02、E05、E06，记录模型配置、请求轨迹和结果；确定性测试通过不等于真实模型已具备组织工作的质量。

真实渠道、OIDC 和外部工具分别用获授权的测试账户验证；没有凭证或服务时明确列为未执行，不把模拟通过报告成真实集成通过。

### 5.2 验证命令基线

以下命令对应现行实现。实际执行结果、模型范围和外部账户限制见[验收记录](collaboration-verification.md)。

```bash
./gradlew check

./gradlew :apps:api:taskE2eTest

```

需要先准备依赖时使用 `pnpm install` 和 `uv sync --all-packages`。Java 命令使用 `./gradlew`；Python 使用 `uv run`，不额外配置 PYTHONPATH。

```bash

```

浏览器场景使用完整 Spring 应用、Web、Temporal Worker 与 Python Runtime，在隔离数据库及队列上执行；不以测试 harness 的简化登录代替完整产品验证。
