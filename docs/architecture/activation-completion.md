# 运行收敛、消息投递与持续推进

更新：2026-10-25。本文描述当前代码已实现的执行机制；业务是否达到目标仍由参与者判断，最终接受仍由确认责任人决定。

## 三种状态分别表达什么

| 对象 | 表达的事实 | 不能由此推断 |
| --- | --- | --- |
| Session 生命周期 | 持续实例仍可接收消息、已暂停或已关闭 | `ACTIVE` 不表示正在推理 |
| Activation 执行 | 一次输入正在排队、执行、已结束或失败 | 执行成功不表示 Task 已完成 |
| Task 状态与决定 | 共享工作的进展、当前版本提交与人的接受 | 口头说“交付”不会生成提交记录 |

参与同一 Task 的实例可用 `session_status(sessionId, taskId)` 查看实际执行状态，无需取得对方私有历史。Task 参数验证共享关系，返回的是该实例的整体忙闲状态，因此不会漏掉未标 Task 的直接消息，也不会把正在处理其他工作的实例误报为空闲；接口不返回其他工作的身份或正文。控制台也使用这一接口；只有具备历史权限时才显示运行记录入口。

## 一次运行必须明确结束

模型通过 `activation_finish` 单独提交本轮结果，不能把它与其他工具放在同一批调用。普通 assistant 文字只记入私有 transcript；“开始整理”“稍后提交”等文本不能触发成功或向用户投递。

| 处置 | 含义 | 运行机制 |
| --- | --- | --- |
| `COMPLETED` | 本轮贡献或回答已完成 | 持久化结果，按需投递一条回复 |
| `WAITING` | 有具体外部依赖 | 必须说明 `waitingFor`，后续消息、工具结果或已配置的安排唤醒原实例 |
| `BLOCKED` | 存在无法自行解决的障碍 | 必须已经报告障碍，或在最终回复中报告 |
| `CONTINUE` | 工作未结束，需要下一段计算 | 保存检查点，自动续执行同一 Activation；不是用户消息 |

如果模型仅输出普通文字就停止，Runtime 会在同次运行中要求继续实际工作或明确结束。连续三次仍不遵循协议则明确失败，不伪造完成，也不无限空转。

`WAITING` 不会凭空创建定时器或订阅：Agent 必须实际发出问题、委派或启动工具；需要未来主动唤醒时调用已授权的安排工具。缺少必要信息或人的接受决定仍是合理的人工接续点。

## 自动续执行与副作用保护

Temporal 在同一个 Activation 内最多执行六段，每次恢复使用原 Session、原 Activation 和持久工具回执。暂时性模型网络错误、429/5xx、执行传输中断、工具步数预算耗尽或 `CONTINUE` 会进入下一段；间隔为 5、10、20、40、60 秒。连续失败或用尽总预算时，只提交一次最终失败通知。

Runtime 的租约阻止重叠执行；恢复先处理已记录的工具调用。已完成的回执返回原结果，未确认的外部写入保留不确定状态；即使模型换一个 call ID，也不能绕过同一操作的未决回执再次执行。此时需要核实外部结果，不承诺所有外部写入都能自动恢复。

每段保存 transcript、工具回执和累计模型用量。已持久化的完成工具可以直接恢复为最终结果，无需让模型重新生成一遍。结果提交使用独立的持久化重试，控制面暂时不可用不会触发模型重跑。

## 一条结果只有一个投递来源

默认把最终答案放在 `activation_finish.reply`；图片、卡片、富文本则先组装内容块，再结束，不同时再放一份相同正文。

当 Agent 已用 `message_send` 向本轮默认接收人发送 RESULT 或 QUESTION，后续自动回复被抑制。控制面按 Activation、接收人和 Task 记录终结消息回执，模型换调用 ID 或改写措辞仍返回原消息。两条机制分别避免“显式发送加自动结果”和“显式工具重复调用”造成重复投递。

这不是按文本全局去重：不同工作的结果、不同收件人和新的协作请求仍独立存在。同一轮对同一接收人和工作应一次组织完整的问题或结果。RESULT 不自动向发送方回一句确认；收到没有新增工作或证据的更新时可以静默结束。模型对不同事件是否值得再汇报，仍需依据其上下文判断。

## 提交必须与当前成果版本一致

`SUBMIT` 将当前共享内容版本提交给确认人；新材料或审阅记录写入后，旧提交失效。命令返回 `status`、`contentRevision` 和 `submissionInvalidated`，让模型明确知道是否需要重新提交。协调者应在所有贡献和审阅记录就绪后读取最新状态，再提交当前版本。

`WAITING` 表示缺少信息，`SUBMITTED` 已表示等待接受。服务端拒绝把已提交工作直接改为 WAITING；只更新阶段说明也不会使提交失效。真正改变目标、共享内容或权限时仍会使原提交失效，防止人误确认旧版本。

## 控制台呈现

- 交流页固定标题与输入区，消息区独立滚动；首次进入定位到最新消息。
- 工作页的标题位于滚动区域之外；桌面工作列表和详情独立滚动，窄屏由内容区整体滚动，不依赖固定页头高度计算吸顶偏移。
- 资料工具栏、内容卡片和卡片内的元信息、正文、操作区使用明确的容器间距。跨区块间距不依赖带负下边距的 `Space wrap`，筛选换行后仍与首张卡片保持距离。
- 表格使用统一边框、间距与横向滚动容器，长文本与工作阶段说明不撑破布局。
- 窄屏保留可展开的工作列表和导航；链接、文本按钮与禁用按钮使用各自样式。
- 运行提示展示实际 Activation 处置；工作页区分实例生命周期和正在执行的状态。
