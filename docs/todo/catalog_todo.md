# Catalog TODO

这份文档记录当前控制面目录侧仍待补齐的工作项。
和 `docs/develop_record/` 中的过程留档不同，这里只保留“当前仍有效”的待办。

## 1. 统一对象级引用分析

现状：

- 已新增统一对象引用分析接口 `GET /api/catalog/references/{objectType}/{objectId}`
- 已覆盖 `domain / scenario / assistant / agent / resource / knowledge_base`
- 已明确 `DIRECT / INDIRECT` 与 `BLOCKS_DELETION / ADVISORY` 两组治理语义
- 资源中心和知识库旧引用接口已复用同一分析结果，删除阻断文案也改为从统一分析派生
- Web 端 `Domain / Scenario / Assistant / Agent / Resource / Knowledge Library` 详情页都已接入统一引用分析面板

对后续工作的意义：

1. `P2.2` 删除前影响预览可以直接复用该协议，不需要再重新设计对象关系模型
2. `P2.5` 资源治理视图增强可以继续沿用同一关系语义和上下文字段
3. 后续若补批量分析，只需要在同一返回结构上扩展批量入口，而不需要推翻当前接口

## 2. 删除前影响预览

现状：

- 当前删除动作大多能被后端正确拦截
- 资源侧已有结构化引用信息，但删除预览仍未形成完整产品流
- 用户往往是在点击删除之后，才知道“为什么不能删”

当前缺口：

- 缺少通用的删除前影响摘要
- 缺少“会阻断删除”和“会被级联回收”的明确区分
- 缺少对发布快照、编排、资源生效版本的影响提示

后续目标：

1. 在删除确认前展示影响摘要，而不是只在失败后提示异常
2. 影响预览至少包含：
   - 阻断删除的对象清单
   - 受影响的发布快照 / 编排 / 绑定关系
   - 自动回收或需要手工处理的对象清单
3. 让单对象删除和未来批量删除共用一套预览协议

## 3. 软删除、归档与治理视图

现状：

- 控制面当前仍以硬删除为主
- 发布快照和资源版本能保留一部分历史锚点，但目录对象缺少统一生命周期状态
- 删除后的对象会直接从主视图消失，不利于审计和恢复

当前缺口：

- 没有 `ACTIVE / ARCHIVED` 之类的生命周期模型
- 没有归档视图、恢复入口和删除原因记录
- 没有“软删除、归档、彻底清理”的边界定义

后续目标：

1. 为核心目录对象引入显式生命周期状态
2. 控制台主视图默认隐藏归档对象，并提供归档筛选或独立视图
3. 为归档对象保留基础元数据、操作人、操作时间、操作原因和删除前引用快照

## 4. 知识库真实导入与检索链路

现状：

- 当前知识库资源已经收敛为“文档集合 + 默认召回数”
- 目录配置中不再保留没有执行语义的外部数据源、切片和 embedding 占位字段
- `agent-runtime` 当前直接基于已发布版本中的文档内容做轻量检索

当前缺口：

- 还没有真实的导入任务、对象存储、解析状态和索引构建流程
- 检索能力仍是轻量闭环，不支持独立的索引治理和召回评估
- 一旦要接真实知识库，目录侧缺少稳定的导入与运维模型

后续目标：

1. 如果重新引入“外部知识源”，必须与真实导入链路一起落地
2. 补齐文件上传 / URL 抓取 / 导入任务 / 失败原因 / 重试等流程
3. 在真实能力存在后，再把切片、embedding、索引、检索模式等字段重新引回正式模型

## 5. 资源治理视图继续补强

现状：

- 当前资源目录已经支持版本流转、生效版本和结构化引用分析
- 资源新建页也已经按 `KNOWLEDGE_BASE / TOOL / LLM_MODEL / SKILL` 四类蓝图收敛

当前缺口：

- 还缺少更完整的批量治理动作
- 还缺少更明确的版本 diff、变更摘要和发布影响展示
- 资源视角和助手发布视角之间的联动还不够强

后续目标：

1. 补齐版本差异摘要和发布影响对比
2. 强化“资源变更会影响哪些已发布助手”的可视化表达
3. 为后续批量发布、批量归档和批量替换资源锚点预留入口
