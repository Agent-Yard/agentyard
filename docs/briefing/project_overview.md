# Lynxus 项目汇报说明

## 1. 项目定位

Lynxus 当前定位为企业智能体平台原型，目标不是提供单点问答能力，而是建立一套围绕智能体协作的治理、发布、运行和观测基础设施。

当前代码库已经超出概念验证阶段，形成了从控制面配置、资源治理、知识发布、助手快照、Temporal 长流程到 Python agent runtime 执行的完整主链。更准确的阶段判断是：

- 单租户默认的企业智能体平台原型
- 可本地联调的 Alpha 阶段产品骨架
- 具备真实发布锚点和人工介入闭环的演示系统

当前不宜定义为生产平台。多租户治理、正式认证鉴权、运行态持久化、审计与成本治理仍未完整落地。

## 2. 项目要解决的问题

企业智能体建设面临的核心问题通常不在模型能力本身，而在系统化落地能力不足，主要表现为：

- 智能体、知识、工具、模型配置分散，缺少统一治理入口
- 运行直接依赖草稿配置，缺少稳定发布锚点
- 多智能体协作链路不透明，运行结果难回溯
- 自动化与人工处理之间缺少平滑衔接机制
- 资源复用、版本控制、引用影响分析能力薄弱

Lynxus 的当前方案，是将这些问题收束到统一平台结构中：

- 用业务域、业务场景、助手、智能体组织治理结构
- 用 Knowledge Base、Tool、LLM Model、Skill 组织能力资产
- 用发布快照冻结运行时真正命中的资源版本与编排图
- 用 Temporal 托管长流程，用 agent runtime 承接节点执行
- 用会话、任务、流程、节点、人工作业记录表达运行态

## 3. 当前阶段结论

当前阶段最关键的结论有四点：

### 3.1 治理主树已经成立

业务域、业务场景、助手、智能体、知识库、资源等核心对象已经形成稳定结构，不再停留在概念建模阶段。

### 3.2 资源治理模型已经落地

Knowledge Base、Tool、LLM Model、Skill 四类资源已经进入统一治理体系，支持版本管理、发布、生效版本和引用分析。

### 3.3 运行模型已经成立

运行不是静态问答链路，而是基于发布快照驱动的真实图编排，支持 `START / AGENT / HUMAN / END` 显式节点执行，且已打通人工暂停与恢复。

### 3.4 平台主链已经闭环

系统已经具备“配置治理 -> 资源绑定 -> 助手发布 -> workflow 执行 -> 人工恢复 -> 运行观测”的完整闭环，具备继续向生产化能力演进的基础。

## 4. 当前已落地能力

### 4.1 控制面与治理能力

- 业务域、业务场景、助手、智能体、知识库、资源的配置管理
- 控制台二级信息架构，覆盖平台设计、助手构建、知识库、能力资源、运行与观测五条主线
- Mock 登录和角色切换，保留后续对接真实身份体系的边界

### 4.2 资源与知识治理能力

- 资源类型收敛为 `TOOL / LLM_MODEL / SKILL`
- 知识库作为独立一级治理对象，而不是助手附属字段
- 资源目录、资源新建、版本发布、生效版本、引用分析
- 知识库工作台、文件导入、URL 导入、文档解析、切片、索引快照、发布版本
- OpenSearch 作为当前正式快照检索后端

### 4.3 发布与冻结能力

- 助手发布时冻结资源版本锚点
- 冻结知识绑定、智能体执行策略和图编排快照
- 运行始终基于发布快照启动，而不是直接读取草稿配置

### 4.4 运行与编排能力

- `START / AGENT / HUMAN / END` 显式图编排
- 基于 Temporal 的 `start / signal / resume` 长流程托管
- Python `agent-runtime` 按发布快照动态执行知识检索、Skill 读取、Tool 调用和模型推理
- `HUMAN` 节点生成 checkpoint 和人工待办，恢复后继续沿图执行

### 4.5 观测与演示能力

- 单助手会话、任务、工作流、节点轨迹和人工介入观测
- Tool 调用摘要、结果摘要、节点状态可回看
- 预置 seed 数据和本地演示闭环，适合方案验证和内部演示

## 5. 当前系统结构

当前仓库采用 monorepo 结构，核心服务划分如下：

- `apps/api`
  Spring Boot 控制面服务，负责目录数据、资源治理、知识库聚合、助手发布、会话与运行实例聚合。
- `apps/worker`
  Temporal worker，负责 workflow 执行、长流程托管和人工 signal 恢复。
- `apps/knowledge-service`
  Python 知识服务，负责内容导入、文档解析、切片、索引快照构建和检索。
- `apps/agent-runtime`
  Python 运行时，负责按发布快照执行图节点，驱动知识检索、Skill 读取、Tool 调用和模型推理。
- `apps/web`
  Vue 控制台，提供配置治理、知识与资源管理、运行与观测界面。

当前本地依赖包括：

- PostgreSQL：控制面与知识服务数据存储
- MinIO：知识对象存储
- OpenSearch：知识快照检索
- Temporal：长流程编排与恢复

## 6. 当前关键设计取舍

### 6.1 以发布快照作为运行锚点

核心目的在于解决配置漂移问题。当前运行实例不直接读取草稿态对象，而是始终基于助手发布快照启动。这样可以保证：

- 运行结果可回溯
- 资源版本可定位
- 后续回滚和审计具备基础

### 6.2 将知识库提升为一级治理对象

知识库不再作为助手内部配置项处理，而是独立管理内容导入、快照构建、发布版本和引用关系。这一设计有利于后续扩展知识生命周期治理和跨助手复用。

### 6.3 将运行图显式化

当前编排采用显式图模型，而不是隐含在 Prompt 或代码分支中的流程逻辑。这样可以让协作结构、人工节点和路由关系更易配置、更易解释，也更容易纳入观测。

### 6.4 将人工介入作为一等能力保留

当前运行模型不是单纯追求自动化闭环，而是允许在流程中显式进入人工节点，并通过 signal/resume 继续执行。这一能力更符合企业场景中的复杂处理链路。

## 7. 当前边界与不足

当前项目虽然主链已经成立，但仍明确保留原型边界，主要包括：

- 默认单租户，复杂租户治理仅保留模型边界
- 认证仍以 mock 为主，尚未接入真实 OIDC / IAM
- 运行态主投影已持久化到 PostgreSQL，并在 API 启动时主动与 Temporal 对账
- `sendMessage` / `launchTask` 仍同步等待 workflow 首个结果
- `demo.local` provider 和 catalog seed 数据仍承担本地演示闭环职责
- 审计、安全隔离、灰度发布、SLO、成本治理尚未形成生产级体系
- Redis / MinIO 等基础依赖的正式职责边界仍有待进一步收敛

因此，当前项目适合定义为平台原型或 Alpha 骨架，不适合定义为生产可交付平台。

## 8. 与长期目标态的关系

`project_description.md` 对应的是更完整的长期目标态，覆盖多租户、权限治理、安全合规、跨域共享、可观测体系、成本治理和更成熟的多智能体平台能力。

当前实现与长期目标态之间的关系可以概括为：

- 长期目标态中的核心对象模型已经有初步落地
- 平台主链中最关键的一段已经做成可运行系统
- 资源治理、知识治理、发布冻结、长流程执行等关键设计已经验证成立
- 尚未进入生产化平台所要求的治理深水区

当前代码库的价值，不在于“功能是否已经完整”，而在于“平台主链是否已经被证明可执行”。这一点已经成立。

## 9. 下一阶段重点

下一阶段建议集中在以下几项工作：

### 9.1 补齐运行态持久化与异步观测

- 将同步等待首结果改造为更完整的异步观测链路
- 在已落地的 runtime 投影基础上强化 workflow 状态查询与运行历史查询能力

### 9.2 引入真实身份与权限体系

- 用真实 OIDC / IAM 替换 mock 认证
- 收敛平台、域、场景、资源的权限边界
- 为后续多租户与跨域共享建立安全基础

### 9.3 强化知识与资源治理闭环

- 完善知识快照生命周期治理
- 补齐删除前影响预览、软删除、归档视图等治理能力
- 强化资源引用分析与发布影响面控制

### 9.4 明确生产化基础设施职责

- 收敛 OpenSearch、MinIO、Redis 等依赖在正式架构中的职责
- 建立监控、备份、恢复和容量规划方案
- 逐步补齐 CI、测试和环境一致性能力

## 10. 汇报结论

Lynxus 当前已经完成从平台概念到可运行原型的关键跨越。项目已经不再停留在对象建模和方案讨论阶段，而是形成了企业智能体平台最关键的一条执行主链：

- 有治理结构
- 有资源体系
- 有知识治理
- 有发布快照
- 有长流程执行
- 有人工恢复
- 有运行观测

当前最准确的判断是：平台骨架已经建立，主链已经闭环，生产化能力仍待补齐。

这一阶段的意义，在于为后续多租户治理、权限体系、运行态持久化、生产级观测与成本治理提供了明确且可持续扩展的基础。
