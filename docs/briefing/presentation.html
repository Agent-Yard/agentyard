项目汇报

当前阶段已经形成从控制面配置、资源治理、知识发布、助手快照、Temporal 长流程到智能体运行时执行的完整主链， 项目已从概念方案进入可运行原型阶段。

阶段判断 Alpha 骨架

已超出概念验证，具备治理、发布、执行、观测的真实闭环。

平台价值 主链已验证

平台最关键的一条执行主链已经可以稳定演示和联调。

当前边界 未生产化

多租户、鉴权、运行态持久化和生产级治理仍待补齐。

01

问题定义

企业智能体落地的共性问题

  • 智能体、知识、工具、模型配置分散
  • 运行直接依赖草稿配置，缺少稳定发布锚点
  • 多智能体协作链路难回溯、难解释
  • 自动化与人工处理缺少平滑衔接
  • 资源复用、版本控制、影响分析能力不足
  • 业务侧、开发侧、运营侧对系统对象理解不统一

Lynxus 当前解决思路

  • 治理结构：业务域、场景、助手、智能体
  • 能力资产：Knowledge Base、Tool、LLM、Skill
  • 稳定运行：发布快照冻结资源和编排图
  • 执行承载：Temporal + agent runtime
  • 运行表达：会话、任务、流程、节点、人工作业
  • 控制台串起配置治理、资源管理与运行观测

演示能力

预置 seed 数据、示例助手和运行会话，适合方案验证和汇报演示。

当前阶段价值

验证了平台主张

证明企业智能体平台不必停留在对象建模和方案描述层，可以落成可运行系统。

统一了系统语言

业务域、场景、助手、智能体、知识库、资源、发布快照、运行实例形成统一表达体系。

收敛了资源治理入口

知识、工具、模型、技能不再散落在多个实现位置，而是进入统一治理对象模型。

建立了继续演进的地基

后续补齐权限、持久化、审计和成本治理时，不需要推翻当前架构主线。

当前阶段最重要的成果不是“功能数量”，而是“已经形成一条可信的可执行主链，并验证了关键设计方向”。
08

关键设计取舍

发布快照作为运行锚点

优先解决配置漂移和运行回溯问题，为后续回滚、审计和版本定位建立基础。

知识库提升为一级治理对象

独立管理内容导入、索引快照、发布版本和引用关系，避免知识能力继续附着在助手草稿配置中。

运行图显式化

将协作结构、人工节点和路由关系从 Prompt 或代码分支中抽离出来，提升可解释性和可观测性。

人工介入保留为一等能力

不追求全自动闭环，而是面向企业复杂链路保留“暂停、接手、恢复”的系统能力。

以本地可联调为阶段目标

优先保证控制台、控制面、知识服务、运行时和基础依赖能够真实联通，提升方案验证效率。

保留长期平台边界

虽然当前默认单租户和 mock 认证，但对象模型和职责划分已为后续多租户与正式治理预留边界。

09

当前边界与不足

原型边界

  • 默认单租户，复杂租户治理仅保留模型边界
  • 认证仍以 mock 为主，尚未接入真实 OIDC / IAM
  • 部分运行态对象仍在 API 内存中维护
  • `sendMessage` / `launchTask` 仍同步等待首个 workflow 结果
  • 部分 provider 和 seed 逻辑仍兼顾演示闭环需求

生产化缺口

  • `demo.local` provider 和 seed 数据仍承担演示闭环职责
  • 审计、安全隔离、灰度发布、SLO、成本治理尚未成体系
  • OpenSearch / MinIO / Redis 的正式职责仍待进一步收敛
  • CI、测试和环境一致性能力仍需补强
  • 运行观测仍偏同步式，尚未形成完整事件化订阅链路
当前最准确的定义仍是平台原型或 Alpha 骨架，不宜直接作为生产可交付平台表述。

明确 OpenSearch、MinIO、Redis 等依赖职责，并补齐监控、备份、恢复和 CI 能力。

  • 资源删除影响预览与归档视图
